# CHORE-SCHEMA-COUNTRY-NAMES-OFF-BY-ONE — the vendored DCS schema names 78 countries wrong

Status: ✅ done

Found on 2026-09-19 while answering a mission maker's build warning about country id `68`. Resolving
that id against the repository's own country table gave **USSR**; the vendored DCS schema, read as a
cross-check, gave **Yugoslavia**. One of the two had to be wrong.

## What was measured

The vendored schema (`src/python/veaf-tools/veaf_libs/data/dcs-schema/dcs-world-api-schema.json`,
frozen at upstream release `v0.3.5`) carries two country tables that disagree with each other:

| | Shape | Verdict |
|---|---|---|
| `types["country.id"].values` | name → id, 92 entries, ids `0..92` with **14 missing** | correct |
| `types["country.name"].values` | id → name, 92 entries, ids `0..91` **with no gap** | wrong from id 14 on |

DCS has no country at id `14` — the repository's own generated table
(`veaf_libs/data/dcs-countries.yaml`, sourced from `dcs-lua-datamine`) has the same hole and the same
`0..92` range. The schema's `country.id` table reproduces it faithfully. Its `country.name` table does
not: it renumbers the names sequentially, so every country after the hole slides down one slot.

Consequences, counted rather than estimated:

- **78 of the 92 names are attached to the wrong id**, starting at `14: ISRAEL` (Israel is 15).
- `68` reads as `USSR` in one table and as the name belonging to id 67 in the other.
- **New Zealand (id 92) is absent from the name table entirely** — it renumbers to 91 and the real 92
  has no entry.

## Why this is a chore and not a fix

Nothing in this repository reads that table. `dcs_mock_audit.py` walks only the `globals` node
(`dcs_mock_audit.py:149`), and every country lookup in the tools goes through `dcs-countries.yaml`,
which is correct. So there is no defect with a victim: **no build, no mission and no test is affected.**

What it costs is a trap for whoever reads the schema. It is vendored precisely to be the reference a
contributor consults, it is the more authoritative-looking of the two sources, and it is wrong for
five countries out of six. That is how this was found: a cross-check against it contradicted the truth.

The file is a **frozen verbatim copy** of a third-party MIT project
([YoloWingPixie/dcs-world-schema](https://github.com/YoloWingPixie/dcs-world-schema)), so it is not
ours to patch — `NOTICE` states the copy is unmodified and `check-vendored` watches it for drift.
Editing it here would make the vendored copy a fork and break both.

## What to do

1. **Report it upstream.** The generator is enumerating names positionally instead of carrying the id
   across. This needs David's go-ahead: it means opening a public issue on someone else's repository.
2. **Warn the reader here**, since the upstream fix will not arrive on our schedule: a line in
   `NOTICE` and a line in the developer documentation (FR + EN) saying that country ids come from
   `dcs-countries.yaml`, and that the schema's `country.name` table is not to be trusted.
3. **Re-check at the next bump.** If a later release fixes it, the warning comes back out in the same
   commit as the new pin.

## Settled: the test guards `country.id` only

Asserted in `test/python/test_vendored_schema_country_ids.py`. `types["country.name"]` is deliberately
left unasserted: a test encoding a known defect reads as intent the day someone repairs it, and would
turn the fix into a red build.

The test covers all 92 entries rather than however many happen to resolve, because a check that
quietly guards less over time is the failure mode its neighbour `test_vendored_pins_match_the_files`
exists to prevent one level up. Five DCS spellings need an explicit alias — two of them upstream typos
ED has shipped for years (`SOUTH_OSETIA`, `CHEZH_REPUBLIC`) — and a sixth name that stopped resolving
would fail the suite rather than silently drop out of coverage.

It was verified to fail, not assumed to: shifting USSR to 67 fails 2 cases, two names sharing an id
fails 2, a country the tools do not know fails 3, and emptying the table fails 1.

**The review caught a defect in the test itself.** Its last case originally asserted that the schema
and `dcs-countries.yaml` describe the *same set* of countries. They do today — but the two files are
updated on independent schedules: our table is regenerated by the weekly DCS Data Drift Watcher, which
opens its own PR (it has done so twice), while the schema stays frozen until someone bumps the pin by
hand. The first time ED adds a country, that assertion would have failed the drift watcher's automated
PR, on an unrelated subject, pointing at the vendored schema — a red build with nothing to fix, on the
side that is right. It now asserts **inclusion in one direction**: the frozen schema may know no
country our table does not. Confirmed by simulation: adding a country to our table alone leaves the
suite green, while every genuine defect above still fails it.

## Measured twice, because the first count was contaminated

The first pass compared the two tables by raw key and reported New Zealand as *absent from the name
table*. It is not: `country.id` spells that one key `NEW ZEALAND` with a space where everything else
uses underscores, so the lookup missed on spelling, not on absence. Re-measured with normalisation:
**78 of 92 still disagree** — the headline figure holds — and id **92 genuinely has no entry**, since
the name table's keys stop at 91. The spelling inconsistency went into the upstream report as a
secondary note, and the reproduction script in that report normalises, so it does not hand the
maintainer a `None` that is an artefact of the check rather than of the data.
