# 04 — The Director: how the AI decides what to do (Foothold v6.5.3)

Scope: the `Director` planner (one instance per side), the passive `DirectorCapability` records it draws from, `BudgetCommander`, `EventCommander`, and the scaling of the AI by difficulty and player count.
Not covered: what a sortie does once launched (`GroupCommander`, see `03-ai-groups-sorties.md`), capture rules, shop internals, CTLD, save-file format.
All line references are to `zoneCommanderv2.lua` unless another file is named.
"(estimation)" marks anything not actually read in the code; "not read" marks code located through the index only.

The `Director` class is about 25 000 lines and 492 methods (`71164-96232`).
The top-level cycle, target scoring, operation build, doctrine choice, phase machine, launch authorisation, finish/learning entry point, reaction entry point and the two small commanders were read in full.
The rest was sampled; each section says what was read.

## 1. Architecture: who decides what

- `GroupCommander` is only the per-sortie state machine; in v6.5.3 it no longer decides on its own when to launch for the roles the Director manages (`95930-96022`).
- `Director` is instantiated twice by the setup file, once per coalition: `redDirector = Director:new({ battleCommander = bc, side = coalition.side.RED })` then `:init()`, and the same for Blue (`MA_Setup_CAv2.lua:6120-6123`).
- Instances are looked up with `Director:getForSide(side)` from a class-level table `instancesBySide` (`71897-71899`, `95903`).
- The Director controls launches by a veto: `Director:allowsGroupSpawn(groupCommander)` returns true only when the group holds an authorised assignment, a routine CAP permit/slot, or a ground permit (`95998-96021`); groups it does not manage always get `true` (`96007`, `96017`).
- It is told of every sortie state change through `Director:onGroupStateChanged(groupCommander, previousState, currentState, wasSpawned, isSpawned)` (`96024-96232`), which marks assignments launched/completed and releases CAP slots and ground permits.
- Three decision loops coexist for Red in PvE: one **operation** at a time (an offensive package against one Blue zone), the **routine CAP** allocation, and the **ground release** (convoys/artillery), plus a **strategic budget** that spends Red credits (`95842-95895`).
- Blue AI in PvE and both sides in PvP run a different, simpler loop `_updateBlue` whose "operation" is support of whatever zone the players are attacking (`95802-95805`, `95709-95800`).

## 2. `DirectorCapability` — the passive sortie catalogue

### Mission-maker view

- A capability is declared inside `zones.<origin>:addGroups({...})` with `DirectorCapability:new({name=..., mission=..., template=..., MissionType=..., targetzone=..., Altitude=..., type=..., condition=...})` (`MA_Setup_CAv2.lua:1290-1297`).
- Examples from Kobuleti: a surface supply convoy to `SAM-India` with a `condition` on a custom flag, two helicopter supplies, a `patrol` CAP over Batumi, an `attack` CAP and a `patrol` CAP over Kutaisi (`MA_Setup_CAv2.lua:1290-1297`).
- The field list and meaning are the same as for `GroupCommander` and are tabulated in `03-ai-groups-sorties.md` section 1 (not repeated).
- The constructor only defaults `id` to `name`, asserts a non-empty id, forbids `update`/`shouldSpawn` methods, defaults `type='air'`, sets `AllowSupplyLaunchFromSuspendedZone` for non-shop supply, and tags the record `_isDirectorCapability` (`11960-11969`).
- `template` is the name of a global Lua list of `.miz` late-activated template group names (e.g. `CapPlaneTemplate`, `HeloSupplyTemplate`, `SupplyConvoy`); the capability's side is derived from the first template whose coalition resolves (`26016-26022`).

### Mechanism

- `ZoneCommander:addGroups` sends tagged records to `BattleCommander:registerDirectorCapability(originZone, capability)` (`56460-56472`, `26280-26298`).
- Registration asserts a unique id, compiles a "facts" prototype and indexes the capability five ways: by origin zone, by target zone, by `mission`, by `MissionType` and by `type` (`26286-26298`).
- The facts prototype is a fake, never-spawned `GroupCommander` look-alike (state `inhangar`, `Spawned=false`) that borrows the template-cache and hangar-delay methods of `GroupCommander`, so that the normal spawn-eligibility code can be run against a capability without instantiating it (`25989-26015`).
- `BattleCommander:evaluateDirectorSpawnEligibility(capability, request)` runs that eligibility on the passive view (`26142-26150`).
- A capability turns into a live `GroupCommander` through `BattleCommander:activateDirectorCapability(capability, request)`, which returns the existing instance if there is one, and allows two extra "derivative" instances in slots 2 and 3 (`26383-26400`).
- When the operation ends the Director asks for the instances to be thrown away: `requestDirectorInstanceDisposal(assignment.groupRef)` for each assignment (`92104-92106`).
- A second source of capabilities is the **DynamicHybrid filler**: `bc:startDynamicHybridFiller(DynamicHybridConfig)` generates capabilities automatically from zone geometry (range limits per role: `airMaxNm=150`, `heloCasMaxNm=40`, `surfaceMaxNm=30`, `minCapAttackNm=35`, `minSeadAttackNm=40`…, and per-zone `forcedZoneCapabilities`) (`MA_Setup_CAv2.lua:6077-6118`), creating `DirectorCapability` records named by origin/target/role (`33861-33876`).
- The Director waits for that filler's bootstrap before its first pass (`94266-94271`).

### Reproduction notes

- The catalogue is data: origin, target, role, template list, predicate; nothing in it needs Moose.
- The subtle part is the "passive view": eligibility (side, template availability, conditions, hangar timers) must be computable without a live group, or the planner cannot count what it could launch.

## 3. The planning cycle (Red, PvE)

### Mechanism (read in full: `95802-95928`)

- `Director:init()` builds a region catalogue and an area catalogue from the setup globals `TheaterRegions`, `TheaterInfrastructure` and `TheaterAreas`, takes the pending save data from the `BattleCommander`, and starts one self-rescheduling `timer.scheduleFunction` (`95898-95928`).
- First run is after `startDelaySec` = 30 s for Red in PvE and 5 s for Blue or PvP; the function returns `scheduleTime + tickSec`, so the period is `tickSec` = 30 s (`95923-95927`, `71869-71870`).
- No Moose scheduler is used by the Director itself; it is raw `timer.scheduleFunction`.
- Until `_runtimeReady()` is true the tick does nothing: it waits for the DynamicHybrid bootstrap and for the air/surface AI and mass-attack save data to be consumed (`94266-94277`).
- On the first ready tick it restores its persistence, or, with no save, enters state `recovery`, schedules the first "surge" after `surgeInitialDelaySec` = 900 s and the first strategic-budget decision after the difficulty profile's `initialDelaySec` (`95810-95841`).
- Each Red PvE tick then runs, in this order (`95842-95895`):
  1. `_updateDefensivePlan` (which Red zones to defend, section 12);
  2. `_consumeAirCombatIntelligence` (where Red aircraft were lost / players fight, section 11);
  3. routine CAP: `_routineCapAwarenessTarget`, `_reconcileRoutineCaps`, `_updateRestoredCapStartup` (section 9);
  4. `_observeRegions`, `_ensureCampaignStrategy`, `_updateStrategicShadow` (campaign-level objective, section 5);
  5. `_reconcileRoutineCapRevector` (re-vector an airborne CAP);
  6. adoption of an externally started mass attack as a `surge` operation, pre-empting the current operation (`95853-95860`);
  7. `_updateStrategicBudget` (spending credits, section 13);
  8. `_updateAirPosture` (section 7);
  9. `_updateGroundRelease` (convoys and artillery, section 10);
  10. if an operation exists: `_reconcileOperationCapacity`, `_updateOperation`, and return (`95876-95881`);
  11. else `_processPendingReaction` (queued counter-attack request);
  12. else, if not in `recovery` and `nextPlanningAt` has passed, `_startOperation`.
- A change of the "capacity signature" (player counts and the five role limits concatenated) while `waiting` forces an immediate re-plan (`95872-95887`, `85626-85637`).
- Director states: `waiting`, `recovery`, `shaping`, `assault`, `exploit`, `surge` for Red; `waiting`/`support` for Blue (`71806`, `94300`, `92011`, `92019`, `92136`, `95731`).

## 4. Target selection and scoring (Red offensive)

### Mechanism (read in full: `84401-84480`, `84767-84886`)

- Candidates are all usable Blue zones that have at least one usable Red neighbour in the "operational" connection graph (`84776-84791`).
- Each gets `score = tacticalScore + 0.35 × strategicScore`, where the strategic score comes from the "strategic shadow" objective list (section 5) (`84792-84799`).
- `_targetScore` starts at 100 and adds or subtracts (`84402-84479`):

| Term | Value | Line |
|---|---|---|
| zone income | `min(40, income × 2)` | `84405` |
| has an airbase | +18 | `84406` |
| has SEAD targets | +18 | `84407` |
| weakness | `(1 − readiness) × 80`, readiness = zone combat-strength ratio or built/upgrade-total | `84408-84412`, `88087-88108` |
| region preference | `_regionTargetPreference(zone,'ATTACK')`: 0 to 90 by region intent and member role, 0 outside a region (section 5) | `84413`, `76959-77019` |
| captured by Blue less than 20 min ago | +160 | `84414-84418` |
| Red neighbours | +35 each | `84419` |
| connectivity | `min(48, connections × 8) + 12 × Blue neighbours` | `84431` |
| front progression | `_campaignFrontProgressionScore`: `min(180, 45 × Red neighbours)`, +100 for a pocket, plus proximity to Red's and Blue's latest captures (section 5) | `84432-84438`, `79233-79309` |
| SAM exposure | `− min(260, exposure × 160)` | `84439-84440` |
| player activity near the zone | `+ playerScores[zone]` | `84441-84442` |
| reactive pressure of Red neighbours | `+ min(20, pressure × 3)` each | `84443-84446` |
| history, same target | +60×age for `near-complete`, +30×age for `partial`, −35/−45/−55×age for aborted/contained/failed (−20×age if freshly captured) | `84456-84465` |
| history, adjacent target (1 hop) | +40×age after a capture/neutralisation there, +18×age after a failure there | `84466-84475` |
| learned target bias | `_targetOutcomeBias` | `84478` |

- `ageWeight = historySize − index + 1`, so the latest operation weighs 3 and the oldest 1 (`84448`).
- Operations that ended administratively (aborted, redirected, pre-empted, or never launched an attacker) do not steer the choice (`84449-84455`).
- The pick is not greedy: `_areaFirstCandidateOrder` first picks an **area** by weighted random among the top three areas of the area recommendation, then `_pickWeightedCandidate` picks by weighted random among the top three candidates of that area (`84832-84886`, `84810-84830`).
- If that preferred target cannot produce an operation, the other candidates are tried in order (same area first) (`94610-94637`).
- Every choice must pass `_campaignActionAdmission` (a "campaign action lease" that prevents flip-flopping between areas; constants: hold 2–5 min, decision 1–2 min, history of 6 over 30 min) (`94585-94596`, `77446-77451`); the scoring is in section 5.

### Player view

- None directly; no message announces the chosen target (the class contains a single `trigger.action.outText*` call, at `72448`, unrelated to target choice).

## 5. Campaign objective: strategy, regions/areas and the "strategic shadow"

Read in full: `_regionTargetPreference` (`76959-77019`), `_selectCampaignStrategy`/`_ensureCampaignStrategy`/`_campaignStrategyShadowBias` (`77057-77332`), the campaign-action arbiter (`77445-77754`), `_strategicShadowCandidateScore` (`78104-78306`), the area half of `_collectStrategicShadowCandidates` (`78308-78427`, `78470-78670`), `_updateStrategicShadow` (`78759-78971`), `_regionIntent` (`76257-76304`), `recordZoneOwnershipChange` (`74800-74824`), `_campaignFrontProgressionScore` (`79233-79309`), the setup catalogues (`MA_Setup_CAv2.lua:2271-2507`).
Not read: `_buildRegionCatalog`/`_buildAreaCatalog` (`74895-75338`), `_buildRegionFacts` (`76105-76256`), `_buildLogisticsIntelligence` (`77938-78074`).

### Mission-maker data (setup file)

- `TheaterAreas` is a list of named areas, each `{id, kind, name, zones = {{name, role}, …}}`; `kind` is `air_network` or `coastal_corridor` on Caucasus, and a zone's `role` is one of `hub`, `gateway`, `defence`, `resource`, `approach` (`MA_Setup_CAv2.lua:2365-2507`).
- Caucasus areas include `western_georgia` (Batumi, Kobuleti, Senaki, Kutaisi as hubs), `abkhazia` (Sukhumi, Sochi), `black_sea_north` (Gelendzhik, Anapa) and `kuban` (Krymsk, Krasnodar-Center) (`MA_Setup_CAv2.lua:2366-2420`).
- `TheaterRegions` describes multi-zone objectives (island groups with `core`, `foothold`, `defence` members) and is empty on Caucasus, so every region-based term below is 0 on this map (`MA_Setup_CAv2.lua:2362-2363`, `76960-76961`).
- `TheaterInfrastructure` entries are `{id, flag, effect = "defence_supply", side, scope = "routes", sourceZone, targetZones}`: a destroyable warehouse, identified by a custom flag, that feeds a SAM zone from a base, e.g. Kobuleti → SAM-India under flag `SamAlphaWarehouse` (`MA_Setup_CAv2.lua:2271-2360`).
- The Director reads `CustomFlags[infrastructure.flag]` to count intact and destroyed infrastructure per area (`78508-78520`).

### Campaign strategy (Red, PvE)

- One strategy is held at a time: `{name, generation, reason, goalZone, goalRegion, selectedAt, weight}` (`77245-77253`).
- It is kept until its goal zone stops being a valid enemy/neutral, active, non-hidden zone (in practice: until Red captures it); then the generation is incremented and a new strategy is drawn (`77267-77286`).
- Selection first floods the operational graph from every usable Red zone to find the reachable non-Red zones (`77083-77103`), then gathers facts over them and picks a goal zone per strategy (`77104-77171`):

| Strategy | Goal zone = reachable zone maximising | Weight in the draw | Lines |
|---|---|---|---|
| `air_supremacy` | `100 if runway + 50 if SEAD targets + 5 × connections + 10 × income` | `1 + 2 × runway targets + 0.75 × SEAD targets` | `77114-77120`, `77186-77193` |
| `economic_pressure` | `100 × income + 10 × connections + 20 if runway` | `1 + 2 × income targets + min(4, total income)` | `77121-77129`, `77194-77202` |
| `island_campaign` | member of an `island` region: role score (core 100, foothold 80, defence 60, other 40) + 70 if Red already holds part of the region + 40 if contested | `2 + 0.8 × region targets + 1.5 × core targets` | `77130-77146`, `77203-77212` |
| `breakthrough` | shadow candidate maximising `hub + 30 if a ground route is open` | `2 + maxHub / 24 + min(3, 0.3 × ground-open targets)` | `77161-77165`, `77213-77219` |
| `counterpunch` | shadow candidate maximising `player + urgency` | `1 + maxPlayer / 60 + maxUrgency / 30`, only if either is > 0 | `77166-77170`, `77220-77228` |

- The draw is a plain weighted random over the available strategies (`77235-77243`); the result is logged with all weights when `config.log` is on (`77255-77263`).
- The strategy then acts through one function, `_campaignStrategyShadowBias`, which fills the `strategy` component of every shadow candidate (`77288-77332`):
  - a route bias common to all strategies: 120 for the goal zone itself, else `max(0, 100 − 12 × graph hops to the goal)` (search limited to 12 hops);
  - `air_supremacy`: +45 for a runway, +25 for SEAD targets;
  - `economic_pressure`: `min(75, 40 × income)`, +40 on the goal;
  - `island_campaign`: in the goal region, core 85 / foothold 70 / defence 45 / other 35, +60 on the goal;
  - `breakthrough`: `0.4 × hub + 20 if a ground route is open`, +60 on the goal;
  - `counterpunch`: `min(100, 0.35 × player) + min(100, urgency)`, +40 on the goal.
- It returns 0 in PvP and for Blue (`77289-77291`).
- It also weighs doctrine choice (section 6) and campaign-action admission (below).

### Strategic shadow: one scored entry per attackable zone

- A candidate's score is the sum of fourteen components (`78107-78122`, `78292-78296`):

| Component | Value | Lines |
|---|---|---|
| `base` | 100 for an enemy zone, 60 for a neutral one | `78108` |
| `player` | player-activity score of the zone, capped 300 | `78109` |
| `runway` | 110 if the zone has a runway capability | `78123-78124` |
| `income` | `min(90, 45 × income)` | `78125-78126` |
| `readiness` | `(1 − target readiness) × 70` | `78127-78130` |
| `region` | `_regionTargetPreference`: by region intent and member role, e.g. `seize_core` core 90, `counterattack_foothold` foothold 90, `reduce_remnant` 75 (+15 defence), `expand_foothold` core 85, `prepare_assault` core 45; +12 if the region is degraded for the enemy, + `min(25, 0.1 × player pressure)`; neutral zones get 75/60/45/35 by role when the intent is to expand | `76969-77018`, `78132-78151` |
| `hub` | `min(48, 8 × connections) + min(36, 9 × connections to non-friendly zones)` | `78153-78162` |
| `urgency` (Red PvE, Blue zone) | +150 if Blue captured it within `captureReactionWindowSec`; + `min(45, 5 × Σ reactive pressure of the Red neighbours)` | `78164-78176` |
| `history` (Red PvE) | same target: +60 × age for `near-complete`, +30 × age for `partial`, 0 for `incomplete`, −80 × age otherwise; a target within 2 hops of a previous one: −20 × age; administrative endings ignored | `78197-78215` |
| `history` (Blue / PvP) | same target: +80/+60/+30 × age for neutralised/near-complete/partial, −80 × age for failed/aborted/contained; within 2 hops of a captured or neutralised target: +30 × age | `78180-78196` |
| `learning` | `_targetOutcomeBias`: `min(30, 10 × success) + min(15, 5 × partial) − min(60, 15 × failure)` on the decayed counters, plus the secondary-axis bias | `78217`, `77431-77442` |
| `commitment` | +100 if it is the running operation's target, +35 if it is already the shadow's main objective | `78218-78224` |
| `logistics` | ready for exploitation: `45 + min(45, 15 × available stock)`; sources open but not ready: `−10 + min(20, 5 × productive sources)`; none open: −40; then `+ min(35, 15 × hub sources) + min(45, 25 × pressured sources) − min(40, 12 × blocked sources) + 20 × (average efficiency − 0.5)`; −30 when there is no logistics row | `78225-78242` |
| `unlock` (Red PvE) | for a SAM zone with SEAD targets whose "defence parent" is the live target (80) or the strategy goal (60), +20 if the parent's supply is ready | `78247-78262` |
| `strategy` | `_campaignStrategyShadowBias` | `78273-78281` |

- Each candidate also carries `effects`: `SECURE` or `CAPTURE`, `AIRFIELD_CONTROL`, `SEAD`, `GROUND_ASSAULT` (a friendly ground neighbour exists and the convoy route is not blocked) or `AIR_ASSAULT`, `LOGISTICS_READY`/`LOGISTICS_BUILDING`/`LOGISTICS_BLOCKED`, `PLAYER_SUPPORT` (`78244-78290`).
- `regionIntent` comes from `_regionIntent`, a decision table on who owns the region's members, its core and its footholds: `inactive`, `consolidate`, `defend_region`, `defend_degraded`, `hold_degraded`, `prepare_assault`, `contain`, `counterattack_foothold`, `reduce_remnant`, `expand_control`, `expand_foothold`, `seize_core`, `observe`; a zone outside any region is `frontline` (`76257-76304`, `78300`).

### Area ranking (the "area shadow")

- Each area gets facts: counts of zones per side (all active zones, and "territorial" zones including suspended ones), a `control` label (`friendly`, `enemy`, `neutral`, `contested`, `mixed`, `inactive`), player pressure, income, intact/destroyed infrastructure, blocked friendly runways, the capability inventory of the area and its neighbours (when the planning inventory is younger than 300 s), and a logistics summary (`78332-78427`, `78478-78555`).
- Area score = sum of (`78562-78662`):
  - `target`: score of its best candidate;
  - `depth`: `0.12 ×` the scores of candidates 2 to 4, capped 140;
  - `player`: `min(90, 0.2 × area player pressure)`;
  - `role`: area roles of the best candidate, hub 70, gateway 55, resource 35, infrastructure 25, defence 20, approach 10, support 5, capped 100 (`78469-78477`);
  - `frontline`: `min(45, 9 × number of candidates)`;
  - `readiness`: `min(70, 6 × combat capabilities nearby)`, or −40 when there are none;
  - `logistics`: `min(70, 12 × stock + 10 × logistics centres) + 20 × efficiency + min(30, 15 × pressured sources) − 30 × blocked-route ratio`, or −35 with no source;
  - `infrastructure`: `15 ×` destroyed infrastructure;
  - `runway`: `− min(140, 20 × blocked runways + 12 × importance + min(60, 0.15 × pressure))`;
  - `continuity` (Blue or PvP only): `180 + min(90, 20 × friendly zones)` when the area is partly held, +220 for the committed area, +260 for the area of the running operation;
  - `history`: ±25 / +12 / +35 × age by the result of previous operations in the area.
- The ranked areas are stored in `areaShadowRecommendation`; this is the list target selection draws its area from (section 4) (`78838-78866`).

### `_updateStrategicShadow`: objective and throttle

- The shadow is rebuilt at most every 300 s unless one of its inputs changed: live target, CAP-target state generation, runway-block generation, region observation signature, player-activity signature, Red reactive pressure signature, strategy name or goal (`78781-78800`).
- A second gate compares a full input signature and skips the rebuild when nothing changed and the logistics intelligence is younger than 300 s (`78801-78809`).
- A zone ownership change forces a rebuild at the next tick for both Directors (`74820-74823`).
- Result `strategicShadowObjective = {main, secondary, candidates, areaShadow, campaignStrategy, campaignGoal, liveTarget}` (`78885-78895`).
- `main` is the top candidate for Red in PvE, and the best candidate of the top-ranked area for Blue and in PvP (`78817-78822`).
- `secondary` is the best candidate on a separate front: another region, or more than 2 graph hops from `main` (`78823-78837`).
- With `config.log`, the main objective, the recommended area and the component breakdown of the top three candidates are logged, only when the signature of the result changes (`78898-78969`).

### Campaign front memory and front progression

- `Director:recordZoneOwnershipChange(zoneName, fromSide, toSide, now)` (class-level, called on every capture) pushes an event `{zone, fromSide, toSide, at}` into a memory shared through the Red Director, capped at `CAMPAIGN_FRONT_EVENT_MAX` = 24, and records the captured zone as the **focus** of the side that took it (`74800-74819`, `71064-71065`).
- `_campaignFrontProgressionScore(target, advancingSide, friendlyNeighbours, enemyNeighbours)` = `min(180, 45 × friendly neighbours)`, +100 when the target has ≥ 2 friendly neighbours and no other enemy neighbour (a pocket), plus proximity to the side's own last capture (180 on it, 125 at 1 hop, 65 at 2, 25 at 3) or, with no focus yet, proximity to the campaign origins (`105 − 22 × (hops − 1)`); for Red it adds proximity to Blue's latest capture while that is within the memory window (180 / 95 / 35 at 0 / 1 / 2 hops) (`79233-79309`).
- The result is cached per memory generation and CAP-target generation (`79240-79254`).
- In the Red target score it is added unweighted next to the connectivity term (`84431-84438`).

### Campaign action admission (the "initiative lease")

- Every Red decision that commits forces passes `_campaignActionAdmission(proposal, now, facts)`; action types are `operation`, `ground`, `upgrade`, `warehouse`, `warehouse_repair`, `mass_attack`, `bomber`, `reaction`, `reactive_cap`, `aien_air_support`, `local_response` (`77452-77464`, `77649-77653`).
- A proposal is `{action, targetZone, areaId, score, urgency 1–3, reason, logistics}`; urgency defaults to 3 when the candidate's strategic urgency is ≥ 100, 2 when > 0, else 1 (`77488-77503`).
- `_campaignActionCandidates` builds two scores, `allow` and `hold` (`77523-77647`):
  - `allow` starts at `70 + min(220, 0.30 × proposal score) + 30 × urgency`; `hold` starts at 75;
  - current workload raises `hold`: `+ min(100, 9 × air commitments)` for an air action, `+ min(75, 18 × ground commitments)` for a ground one;
  - if a lease is active: aligned with it (same target, or same area and both actions of a "support" type) → `allow` +140; not aligned → `hold` +140 and `allow` + `55 × (urgency − 1)`;
  - if an operation is running: same target or area → `allow` +90; elsewhere → `hold` +120 (except for `upgrade`);
  - strategy: goal zone +70, goal area +30, and +30 to +40 when the action type suits the strategy (e.g. `breakthrough` with `operation`/`ground`, `counterpunch` with reactions and upgrades);
  - defensive plan: +70 for a defensive action in the primary defended zone or area;
  - supply: `+ min(45, 25 × supply sorties already heading to the target)`, +35 for a defensive action when sources are under pressure;
  - repetition: over the last 6 actions within 30 min, `− min(45, 6 × age weight)` for the same action type and `− min(35, 5 × age weight)` for the same target;
  - urgency 3 adds +170 to `allow`.
- Decision: an aligned proposal is always allowed; a proposal that already waited out a `hold` and meets no lease is allowed; otherwise it is a weighted random between `allow` and `hold` proportional to the two scores (`77678-77685`, `84810-84830`).
- The decision is cached by signature (`action|target|urgency|reason`) for 60–120 s, so the same proposal is not re-rolled every tick (`77658-77664`, `77697-77703`).
- `_commitCampaignAction` creates the lease when the committed action is not aligned with the current one: `{action, targetZone, areaId, urgency, generation, holdUntil = now + 120–300 s}`, and pushes the action into the 6-entry history (`77707-77754`).
- Effect: for 2 to 5 minutes after Red commits somewhere, actions in the same area are waved through and actions elsewhere must win a draw weighted against them.

## 6. Building an operation: doctrine, package, feint, reserve

### Mechanism (read in full: `89947-90128`, `87409-87527`, `87630-87890`, `88018-88085`)

- **Package size.** `_currentPackageMaximum(players) = max(configured air capacity, min(6, max(1, 2 + floor(players/2)))) − strategic bomber cost` (`85639-85649`).
- "Configured air capacity" in PvE is `CAP + CAS + SEAD + RUNWAYSTRIKE limits (+1 if CAS > 0)` (`85619-85623`).
- The role limits are the global difficulty/player-count functions `getCapLimit(bluePlayers)`, `getRedCasLimit`, `getRedSeadLimit`, `getRedRunwayStrikeLimit`, `getRedAntiShipLimit(redCasPlayers)` (`85517-85527`); those functions are described in `03-ai-groups-sorties.md` section 3.
- `playerCount` for Red planning is `getRedCasPlayersCount()` (`95852`).
- The air posture then narrows the size (section 7) (`94563-94567`).
- **Doctrine.** If the target was captured by Blue within `captureReactionWindowSec`, doctrine is `counterattack` (`87411-87413`).
- Otherwise a weighted random among the doctrines that are feasible (`87456-87489`):
  - `suppression` if the target has SEAD targets, the SEAD limit is > 0 and a SEAD group exists;
  - `isolation` if the target has a runway, Blue runway air support is worth something, and a runway-strike group exists;
  - `ground_push` if artillery or surface groups exist, a supply group exists and "exploitation supply" is ready;
  - `counterattack` if the strategy is `counterpunch` with player pressure, or the region intent asks for it;
  - `air_assault` if any CAS, CAP or anti-ship group exists;
  - `probe` always.
- Each doctrine's weight = base (1 for `probe`, 3 for others) × learned performance clamp [0.75, 1.35] ÷ repetition penalty from `history` × situational bias (1.75 when its precondition is strong, plus strategy bonuses) (`86853-86888`, `87432-87454`).
- **Pools.** `_collectExactRouteGroups(targetZone, …, planningInventory)` returns per-role candidate lists `CAP`, `CAS`, `SEAD`, `RUNWAYSTRIKE`, `ANTISHIP`, `ARTY`, `SURFACE`, `SUPPLY` of capabilities whose `targetzone` is exactly that zone (`86313-86571`, body sampled only; pool names from `94316`, `87471-87479`).
- **Role filling (Red).** A CAP is taken first when CAP is allowed and the package has more than one place (`87725-87737`); a "SEAD loss escort" CAP may be added (`87738-87749`).
- Then roles are drawn one at a time by weighted random from `RED_PACKAGE_ROLE_CHOICES` until the package is full or nothing is available (`87750-87835`).
- Weight of a role = doctrine table weight (`RED_PACKAGE_ROLE_WEIGHTS`, `71066-71073`) × √(role limit) × learned role outcome [0.8, 1.2] × combined-arms multiplier × battlefield-intelligence multiplier ÷ (1 + 1.5 × already selected) (`87769-87780`).
- Situational multipliers: SEAD ×1.8 with long-range SAMs else ×1.3; CAP × (1 + min(1.5, playerPressure/120)); CAS × (1 + min(1, built/12)), and with long-range SAMs helicopters ×1.4 and planes ×0.55 (`87781-87792`).
- SEAD is only eligible if the target has SEAD targets; a runway strike only if the target has a runway, the strike is "worthwhile", none is already selected, and a SEAD is already in the package when SAMs are present (`87760-87764`).
- SEAD, CAP and runway strike belong to phase `shape`; CAS (plane or helicopter) and anti-ship to phase `assault` (`71074-71081`).
- **Ground part.** A ground budget per doctrine (`suppression` 1, `isolation` 0, `air_assault` 1, `counterattack` 2, `ground_push` 2, `probe` 0) plus an "opportunity" extra from runway strain, player pressure and player count, capped at 4, is filled with `SURFACE`/`ARTY` by weighted random (`87837-87890`, `71082-71093`).
- **Feint / secondary axis.** With ≥ 4 players and a package of ≥ 4, with probability `min(70, 25 + 10 × (players − 4))` %, one CAS (else CAP) is sent against another candidate at least 3 graph hops away; the main body is then delayed by 240–420 s (`90030-90083`, `87492-87527`).
- With ≥ 6 players the feint prefers a different area (×1.35) (`87496-87508`).
- **Reserve.** For non-reaction, non-probe packages of ≥ 3 air groups with ≥ 2 main attackers, with 35 % chance one assault CAS is held as a conditional reserve, earliest after 120–240 s and at the latest (fallback) after 360–720 s (`88027-88085`).
- If no attacker could be assigned the operation is dropped; if only CAP could be assigned the doctrine is relabelled `probe` (`90111-90116`).
- `SUPPLY` assignments are never launched by the operation: they are cancelled with reason `regular-supply-owned`, supply being owned by the regular supply system (`91826-91827`).

### Reproduction notes

- The assignment record is the central object: `{name, groupRef, role, capacityRole, phase, targetZone, sourceZone, unitCategory, authorized, launched, completed, cancelled, detached, reserveHeld, …}` (fields seen at `95979-95987`, `91782-91910`).
- Everything is weighted-random with deterministic tie-breaks, never arg-max: the same situation produces different packages.

## 7. Air posture (Red package sizing by loss and runway state)

Read in full: `71149-71441`.

- Every time the previous posture's hold expires, Red picks one of four postures by score, choosing randomly (score-weighted) among those within 66 % of the top score (`71396-71414`, `71151`).
- `conserve`: `35 + lossRatio×220 (+80 if < 40 % CAP serviceable) (+40 if a bomber or mass attack is running) + runwayStrain×130` (`71349-71353`).
- `disperse`: `65 + 4×players + 30×fronts(max 5) + 50×lossRatio + 115×runwayStrain + 10×affected runway areas` (`71356-71361`).
- `pressure` (needs ≥ 30 % serviceable): `70 + 7×players + 60×serviceable + min(40, 0.1×maxPressure) − 100×lossRatio − 30 if strategic conflict − 65×runwayStrain` (`71362-71368`).
- `concentrate` (needs ≥ 4 players, ≥ 65 % serviceable, 1–2 fronts, no operation running): `80 + 8×players + 80 (one front) or 35 + 70×serviceable − 140×lossRatio − 140×runwayStrain` (`71369-71376`).
- Hold times: conserve 8–14 min (and no operation for the first 2–5 min), disperse 6–10, pressure 7–12, concentrate 9–15 (`71152-71162`).
- Effect on the next operation's size, with `playerScaled = min(6, max(1, 2 + floor(players/2)))`: conserve ≤ 2; disperse between half and `playerScaled`; pressure between `playerScaled` and `playerScaled + 2`; concentrate between `max(4, playerScaled + 2)` and `playerScaled + max(2, 0.75×players)`; minus the routine CAP already airborne; the final size is a uniform random in that range (`71179-71206`).
- `lossRatio` = max(CAP slots cooling after a combat loss, recent air-loss score ÷ 80) ÷ total CAP slots (`71233-71246`).
- `runwayStrain` grows with blocked Red runways, their importance and pressure (`71271-71275`).

## 8. Operation phases, launch clearance, reassessment, end

### Phases (read in full: `94643-94735`, `91774-92109`)

- `shaping`: authorises `feint` assignments at once and `shape` assignments (SEAD, CAP, runway strike) from `mainAuthorizeAt`; moves to `assault` when CAP coverage is active and feint and shape phases are "settled" (all launched or completed), or at the 720 s deadline; if the deadline passes without CAP coverage the operation is "contained" (`94696-94713`).
- `assault`: authorises `assault` assignments (CAS, anti-ship, surface, artillery), possibly with CAS blocked by the SEAD gate; goes to `exploit` when the target turns neutral; fails when all combat groups are complete or at the deadline (`94714-94726`).
- The assault deadline is `assaultMaxSec` plus a travel-time allowance: the longest source-to-target distance of the unlaunched CAS at 120 kt (helicopter) or 350 kt (plane), capped at another `assaultMaxSec` and by `operationMaxSec` (`91983-92006`).
- `exploit`: 900 s to let a capture happen; ends `captured`, `neutralized` or `failed` (`94727-94733`).
- At any time: target inactive/hidden/suspended → `aborted`; target now Red → `captured`; age ≥ 3600 s → `neutralized` or `failed` (`94662-94674`).
- `surge` (mass attack) simply waits for the external mass-attack mission to end and reads the zone side (`94646-94661`).

### Launch clearance

- "Authorising" an assignment does not spawn anything: it sets `assignment.authorized = true`, clears the group's spawn-evaluation cache and dormant delay, and wakes its FSM (`91897-91909`, `82650`); the actual spawn is the `GroupCommander`'s own, which asks `allowsGroupSpawn` (`96017-96021`).
- An assignment is refused this tick (left unauthorised) when: the runway strike waits for SEAD (`91828`), the operation waits for its CAP (`91832`), SEAD waits for an ingress CAP (`91836-91837`), the role is blocked by the SEAD/CAS gate (helicopters exempt) (`91841-91843`), no role slot is free (`91847-91849`), or another surface group was already authorised from the same source zone this tick (`91860-91862`).
- An assignment is cancelled when the feint target became unusable, the origin zone is no longer usable, or an attack CAP's target is no longer "player-relevant" (`91786-91800`, `91819-91825`).
- **SEAD/CAS gate**: CAS planes are held while long-range SAM threats lie within 45 NM of the target; the gate is rechecked every 30 s for at most 2 SEAD attempts, after which it can fall back to ground forces, redirect or contain the package (`71004-71006`; functions `88955-89031`, `88519-88600` located by name, exact sequence is (estimation)).
- **SEAD ingress CAP**: a CAP is positioned within 30 NM of the SEAD ingress point, with a 180 s spawn delay and a maximum hold of 360 s (`71008-71013`; `88800-88955` not read).
- **Red package CAP protection**: fixed-wing attackers are cancelled when no CAP can protect them under air pressure (`90668-90685`, `90862-90979` not read, (estimation) from names).

### Reassessment (read in full: `89398-89541`, `89828-89903`)

- Every 90 s during `shaping`/`assault`, and at each phase change, but acting only once the operation is ≥ 180 s old (`70999-71001`, `89836-89843`).
- Inputs: target strength now vs baseline (−10 % since last look or −20 % since start = "weakening"; the reverse = "strengthening"), package losses, the best alternative objective and the player-activity component of both (`89408-89417`, `89442-89463`).
- "Bad fight" = ≥ 2 launched and loss ratio ≥ 60 % (75 % for an important target: score ≥ 170, runway or income) without weakening (`89446-89455`).
- Redirect evidence = a redirectable (unlaunched) part exists and either the players moved (alternative player score ≥ 100 and ≥ current + 80) or the alternative is better by ×1.35 or +80 combined with a bad fight / reinforcement / loss of the current candidate (`89458-89469`, `71002-71003`).
- A redirect needs the same alternative on 2 consecutive reassessments, is allowed once per operation and never for a reaction operation; it re-targets only the unlaunched groups (`89861-89891`; `89645-89814` not read).
- Otherwise "contain": cancel everything unlaunched and finish with result `contained`, when the main attackers are exhausted without progress or the fight is bad (`89893-89901`, `89814-89826`).
- The reserve is released on "target weakening" or "player pressure" (player score ≥ 100 with losses < 50 %), or as a "delayed wave" at the fallback time; it is cancelled ("conserved") on a bad fight (`89471-89478`, `89905-89945`).

### End of operation and learning (read in full: `92026-92109`, `89369-89396`, `86853-86904`, `73295-73364`, `88110-88129`)

- A `failed` result is upgraded from the destroyed share of the target's initial strength: remaining ≤ 10 % → `near-complete`, destroyed ≥ 25 % → `partial`, ≥ 10 % → `incomplete` (`88110-88129`).
- The learning outcome is `success` (captured), `partial` (neutralised, near-complete, partial, or "meaningful progress"), `failure` ("committed, no progress"), or nothing when no attacking element launched or the deployment was incomplete (`89369-89396`).
- It is credited, weighted by a causal assessment (`_operationCausalAssessment`, `89244`, not read), to three decayed counters: `doctrineOutcomes[doctrine]`, `targetOutcomes[zone]`, and `roleOutcomes[doctrine][role]` (`92043-92076`, `87387`).
- The counters are capped at 99 and decay with the battlefield-intelligence half-life of 45 min, expiring after 3 h (`73323-73332`, `73295-73321`, `71037-71038`).
- Use: doctrine weight × clamp((success + 0.5×partial + 1)/(failure + 1), 0.75, 1.35); role weight × (0.8 + 0.4 × (success + 0.5×partial + 1)/(total + 2)) (`86857-86860`, `86890-86904`).
- A 3-entry `history` (`targetZone`, `feintTargetZone`, `sourceZone`, `doctrine`, `result`, learning outcome and reason) drives the repetition penalty and the target-history terms (`92091-92100`).
- Then all groups are released, on-demand instances are disposed, and the Director enters `recovery` for 600–1200 s (`92101-92108`).

## 9. Routine CAP management and defensive air reactions

Read: `_routineCapAllocation` (`81380-81467`), head of `_reconcileRoutineCap` (`81469-81530`), `requestReactiveCap` (`72634-72753`), head of `requestPlayerCapResponse` (`81160-81215`), CAP branch of `onGroupStateChanged` (`96077-96133`), slot helpers (`71926-71941`), loss-readiness profiles (`71582-71610`).
Not read: the bulk of `_reconcileRoutineCap` (`81530-82026`), `_rankCapTargets`/`_routineCapTargetValue` (`80675-80876`), re-vectoring (`82044-82367`), `_syncCapSlotOccupants` (`72225-72395`), `_advanceCapLossRecovery` (`71624-71800`).

### Mechanism

- CAP is managed through **slots**, not through groups: slot ids are `patrol:<n>`, `attack:<n>` and `reaction-<mission>:<n>` (`71926-71929`).
- Each tick `_routineCapAllocation` sets the slot capacity to the base CAP limit for `patrol` and for `attack` (plus the reaction allowance on `attack`), so the total is `2 × baseLimit + reactionExtra`; `baseLimit` is `getCapLimit(bluePlayers)` (`81382-81389`, `85517-85518`).
- This matches the Config comment "1 amount equals 1 CAP Patrol and 1 CAP Attack" (`Foothold Config.lua:889`).
- The free slots are distributed between `patrol` (defensive, over own zones) and `attack` (offensive, over enemy zones) by marginal demand: `demand.score / (1 + 0.85 × already allocated)`, ×1.25 while under the base limit, with a minimum of one each when the demand is non-zero (`81410-81450`).
- A slot has a lease kind (`routine`, `operation`, `active`), a state (`authorized`, `preparing`, active…) and a `readyAt` cooldown (`96084-96125`, `95976`, `95995`).
- A new slot's first availability is the side's `respawnTimers[side][mission].hangar` plus a jitter of 60 s to 25 min; after a combat loss it is `dead + hangar` plus 0–25 min (`71931-71941`, `71047-71048`).
- Loss recovery speeds up with player count, by difficulty (`RedReactiveDifficulty`): easy needs ≥ 3 players, 1 slot max, progress rate 0.5, floor 20 min; medium ≥ 3 players, up to 3 slots, rate 1–2, floor 10 min; hard ≥ 2 players, up to 4 slots, rate 1.5–2.5, floor 10 min (`71582-71610`; how the rate is applied is in `_advanceCapLossRecovery`, not read).
- State changes drive the slot: `preparing` → marked preparing; live → active; `landed` → released "after handover"; `dead` from an airborne state → released "after loss" (long cooldown); `dead`/`inhangar` from `preparing` → released as `spawn-failed` with a 120 s permit retry (`96093-96132`).
- A "routine CAP permit" (`routineCapPermits[groupName]`) is the Director's election of one specific group for a slot; `allowsGroupSpawn` returns true for a routine-CAP group only if it is live, its slot is authorised/preparing, it holds an authorised assignment, or it holds a permit (`95998-96005`).
- **Player arrival**: when the Blue player count increases (PvE), the player-tracking loop calls `redDirector:requestPlayerCapResponse(now)`, which, if no Red CAP is airborne or preparing, elects the best-ranked in-hangar CAP for the best-ranked CAP target (`60801-60803`, `81160-81215`).
- **Reactive CAP**: the Red reactive system calls `requestReactiveCap(zone, allowance)` when players press a Red zone; the Director checks the zone ranks within the CAP target window, counts available responses, passes campaign-action admission and stores an `aienAirSupportRequest` with `explicitReaction=true` valid 20 min, which adds up to `reactionCapExtra` slots to the patrol limit (`31468`, `72634-72753`, `81501-81519`).
- **AIEN air-support call**: when a player aeroplane attacks a Red zone's ground forces (reported by AIEN through `BattleCommander:reportAIENAirSupportAttack`), at most once per 20 min, with a 10 % chance, the Director creates a patrol-CAP request for that zone and Blue receives the message "C2, intercepted enemy communications: %s has requested air support." for 15 s (`71901-71905`, `72414-72456`, `70995-70997`, `Foothold_Localization.lua:21118`).
- **Re-vectoring an airborne CAP** towards where air combat happens is limited to an ETA of 15 min and driven by the air-combat intelligence (section 11) (`71030`, `82184-82367` not read).
- **Hunter** (a two-ship scrambled after a player's kill streak) and the strategic-bomber interceptor roll are separate mechanisms outside the Director (see `03-ai-groups-sorties.md` sections 8 and 12).

### Reproduction notes

- The slot abstraction is what keeps the number of CAP flights stable when groups die, are re-tasked or are borrowed by an operation; a re-implementation that counts live groups only will oscillate.
- The CAP target ranking (`getClosestCapZonesToPlayers`, `CapTargets`, `CapRef`) lives outside the Director and is shared with `GroupCommander` (`85685`, `72668-72672`).

## 10. Ground release (convoys and artillery)

Read in full: `85257-85476`, `84922-84932`, `85184-85210`, ground branch of `onGroupStateChanged` (`96035-96073`).

- Runs for Red only, every `groundDecisionSec` = 90 s (`85420-85423`).
- Limits by Red-CAS player count: `SURFACE` 1 (≤ 2 players), 3 (≤ 5), 4 (more); `ARTY` 2 (≤ 5 players), 3 (more); one artillery per target (`84922-84932`, `85277`).
- Candidates are every surface/artillery group or passive capability whose origin zone is usable and whose target is in the current offensive target list, not blocked by `IsGroundConvoyBlocked(source, target)` (`85312-85326`, `85281-85287`).
- Score = the target's offensive score, +35 if the target has no ground commitment yet, +20 if the source has none, −70 per commitment on the target, −40 per commitment from the source, −90 per commitment on the same pair, −0.35 × distance (NM, capped 180), −6 × graph hops (capped 8), +80 if it is the current operation's target, minus history penalties over the last 8 releases (`85184-85210`, `84898`).
- Only the 12 best are tested for real spawn eligibility and at most 6 are short-listed; `SURFACE` candidates lose a penalty for current player presence within 25 NM of their route (max 180) (`85432-85447`, `84899-84900`, `71043-71044`).
- The release is probabilistic: chance = 1 when nothing is committed, else `clamp(0.25 + 0.35 × targetSignal + 0.30 × min(1, players/9) − 0.20 × workload, 0.10, 0.90)`; then a weighted pick among the top three (`85337-85370`).
- Authorising creates a **ground permit** valid `groundPermitTimeoutSec` = 12 min, instantiates the capability if needed and wakes its FSM; a suspended source zone is given `_suspendAllowSpawn` (`85372-85417`).
- On launch the permit is marked launched; on spawn failure it is released with a 120 s retry; on sortie completion a reuse cooldown is set and an on-demand instance is disposed (`96049-96072`).

## 11. Intelligence memories ("learning" about the battlefield)

Read: `_consumeAirCombatIntelligence` head (`72928-72990`), constants (`71018-71046`), `_playerFrontlineActivityScores` head (`75689-75760`), outcome decay (`73295-73364`).
Not read: `_consumeBattlefieldIntelligence` (`74135-74311`), route-risk functions (`73442-73810`), the scoring body of `_playerFrontlineActivityScores` (`75760-75990`).

- **Player frontline activity**: a per-zone score of where human players are and what they do, plus an air-threat variant (`capOnly`); cached for 15 s; it also yields `humanPlayers`, `frontCount` and `maxPressure` used by the air posture (`75689-75705`, `75712`, `71249-71252`).

- Its users in the read code: role weights in the package (`87779`), SEAD escort risk (`87661-87662`), CAP placement value and supply-protection requests (`73638-73760`, not read).

- **Campaign front memory** and the **history** lists (operations 3, ground releases 8, strategic purchases 6, campaign actions 6) complete the memory (`71879`, `84898`, `84226`, `77450`).

## 12. Reactions to the players' offensive (Red)

Read in full: `requestReaction` and its queue (`94279-94560`), the reactive tick caller (`31715-31784`), profiles (`31055-31135`), CAS diversion decision (`84482-84521`, `84736-84766`), `_updateDefensivePlan` head (`76847-76905`).
Not read: `_airReactionDecision` (`71495-71545`), `_buildDefensivePlanProposal` (`76724-76827`), `requestEnemyPositionResponse` (`72458-72558`), `_capturedZoneCasAssignmentFacts` (`84562-84667`).

- The **Red reactive counter-pressure** loop belongs to `BattleCommander` (`bc:startRedReactiveCounterpressure(RedReactiveConfig)`, `MA_Setup_CAv2.lua:6125-6127`) and is the Director's sensor: it computes a pressure value per Red zone from nearby players and processes at most `maxZonesPerTick` = 1 zone per tick (`31724-31742`, `31073`).
- "Soft" reaction (pressure ≥ `minPressureSoft`): boosts supply and CAP for the zone (`31744-31751`).
- "Hard" reaction (pressure ≥ `minPressureHard`, or a Blue capture of a neighbouring zone within `captureHardWindowSec`): optionally asks the Director for a zone upgrade, then calls `director:requestReaction({targetZone, sourceZone, reason='capture'|'pressure', allowance=hardForcePerZone, capAllowance, groupReuseCooldownSec})` (`31753-31781`, `31683-31696`).
- Difficulty profiles (`RedReactiveDifficulty`, default `"medium"`, `Foothold Config.lua:438`): soft/hard thresholds 9/12 (easy), 6/9 (medium), 3/6 (hard); player distance 75/75/120 NM; capture window 120/180/240 s; zone cooldown 1800/1800/900 s; forced groups per zone 1/2/3; extra reaction CAP 0/1/2; zone upgrade off/on/on; AIEN air support off/on/on; group reuse cooldown 1600/1200/900 s (`31064-31127`).
- `requestReaction` (PvE only) normalises the request (priority 2 for `capture`, 1 for `pressure`), asks `_airReactionDecision` how much air it can afford (it returns an allowance, a CAP allowance, a mode such as `limited`, and a hold of 5–10 min), then (`94475-94560`, `71443-71444`):
  - if the Director is not ready or a surge is running: queue;
  - if an operation already targets the same zone in `shaping`/`assault`: reinforce it (`_augmentReactionOperation`);
  - if the reason is `capture` and another operation runs: build a replacement and finish the current one as `redirected-by-reaction`;
  - if idle: build a reaction operation at once (it bypasses `recovery` and `nextPlanningAt`);
  - otherwise queue.
- The queue holds a single pending request; a same-target request raises its allowance, a higher-priority request replaces it, and it expires at the air decision's hold time (`94334-94378`, `94419-94426`).
- A reaction operation gets `urgency` 3 (capture) or 2 (pressure) and, for a fresh capture, the `counterattack` doctrine (`94443`, `87411-87413`).
- **CAS diversion on capture**: when Blue captures a zone, `considerCapturedZoneCasDiversion` scores each airborne CAS of the current operation for re-tasking onto the captured zone (distance, ETA, target score, player score, weakness of the captured zone, remaining fuel ≥ 20 %, remaining attack weapons ≥ 30 % of the template); it diverts the best one if the score reaches 60 (`56709`, `84482-84521`, `84736-84766`, `71015-71017`).
- **Runway destroyed**: `redDirector:onRunwayDestroyed(zone)` is called when a runway is destroyed, and runway strikes on a target cool down for 60 min (`42916`, `71014`, `82587-82641` not read).
- **Defensive plan**: each tick Red computes a primary and a secondary zone to defend from player activity, the Blue Director's operation focus and Blue's own strategic objective; the proposal is cached while its inputs are unchanged (up to 60 s), must be held at least 5 min, and a switch needs 2 confirmations (`76847-76905`, `71059-71063`).
- The plan is used for supply priority (+45 primary, +25 secondary) and for the ground-route threat list (`77872-77885`, `95875`).

## 13. Economy decisions: strategic budget, zone upgrades, supply priority

Read in full: `84006-84398`, `83448-83467`, `77825-77937`, `BudgetCommander` (`96236-96289`); head of `selectZoneUpgradeTarget` (`83296-83330`).
Not read: `_strategicBudgetFacts` (`83517`), `_strategicBudgetUpgradePlan`/`_zoneUpgradeScore` (`83156-83233`, `83911`), `_strategicWarehousePlan` (`83929`), `_buildLogisticsIntelligence` (`77938`).

### Red strategic budget (Director)

- Red in PvE only; a decision every `decisionSec` (180/120/60 s by difficulty), first one after 20/15/10 min (`84318-84328`, `71108-71148`).
- Five purchasable actions, each a Red shop item: `upgrade` → `redzoneupgrade`, `warehouse` → `redwarehouse`, `warehouse_repair` → `redwhrepair`, `mass_attack` → `redmassattack`, `bomber` → `strategicbomberRed` (`71099-71105`).
- Candidate scores (`84020-84148`):
  - `upgrade`: `(200 + min(240, 0.35 × plan score) (+400 if demanded by a reaction)) × upgradeWeight`; considered if demanded, or affordable within `saveHorizonSec`;
  - `warehouse`/`warehouse_repair`: from `_strategicWarehousePlan`, only outside the spend cooldown;
  - `mass_attack`: `(260 + min(180, 0.30 × target score) + min(120, 25 × players) + min(100, 0.5 × urgency)) × massAttackWeight`; needs no other strategic air action, a posture other than `conserve`, ≥ 55 % serviceable CAP and < 55 % losses, the surge cooldown elapsed, and at least `massMinPlayers` (4/3/2) players;
  - `bomber`: `(230 + min(180, 0.30 × target score) + 40 if runway + min(60, 15 × income)) × bomberWeight`; needs ≥ 40 % serviceable CAP, < 60 % losses and the bomber cooldown elapsed.
- A previous "intent" for the same action adds +35 (stickiness) (`84013-84016`).
- Decision: buy the top candidate if affordable; otherwise **save** for it if income will cover the shortfall within the save horizon (shorter for urgent items); otherwise buy an affordable fallback scoring at least `fallbackScoreRatio` (0.75/0.60/0.45) of the top; a spend cooldown of 30/20/15 min follows each purchase (`84160-84192`, `84210-84216`).
- Execution goes through the normal shop (`battleCommander:buyShopItem(side, itemId, …)`), with preferred target lists passed to the mass attack and the bomber; a failed purchase blocks that action for max(60 s, `decisionSec`) (`84230-84298`).
- A purchased mass attack is adopted as a `surge` operation; the next surge is not before 2700–5400 s (`84274-84276`, `92136-92137`).
- Available credits = account minus credits reserved by pending shop purchases (`84238-84239`).

### `BudgetCommander` (legacy random buyer)

- A tiny class: every `decissionFrequency` (+ random `decissionVariance`) it lists the affordable shop items of its side and, unless a `skipChance` roll says no, buys one at random (up to 10 tries, each subject to the item's `aiPurchaseChance`) (`96246-96288`).
- It uses Moose `SCHEDULER:New(nil, fn, {self}, delay, repeat)` (`96281-96288`), which wraps `timer.scheduleFunction`.
- It yields to the Director: `update` returns immediately if `director:ownsRedStrategicBudget()` (Red Director started and enabled) and for Red in PvP (`96247-96249`, `83458-83460`).
- No `BudgetCommander:new` exists in any setup file of the v6.5.3 extract (searched all `.lua` files): the class is dead code in this version.

### Zone upgrades and supply priority

- `Director:requestZoneUpgrade(context)` records a demand (pressure zone, Blue-occupied zones, reason, cooldown) that the budget then prices and schedules; it is called by the Red reactive tick when players strike a zone (`31761-31771`, `83431`).
- `Director:selectZoneUpgradeTarget(zoneChoices, context, now)` is called by the shop's zone-upgrade action to pick the zone and the upgrade slot: it scores each candidate zone not occupied by Blue and inside the "upgrade corridor" of the pressure zone using a defence profile per category (`sam`, `shorad`, …) (`24130`, `83296-83330`).
- `Director:regularSupplyTargetPriority(targetZone, context)` gives the regular supply system a per-zone priority made of: area role (hub 50, infrastructure 45, gateway 40, resource 25, defence 20, approach 15), income (max 40), player pressure (max 90, plus Red reactive pressure max 100), operation focus (120, or 50 for the same area), defensive plan (45/25), strategic objective (90 main, 45 secondary), area recommendation (45/25), fresh capture (100, Blue side), and campaign strategy bonuses (`77825-77937`, called at `54488`).
- So supply/recapture/upgrade choices are not made by the Director's operation; the Director only supplies priorities and admission to the supply system (`BattleCommander:_regularSupplyTargetPriority`, `54443-54488`).

## 19. Cost of a planning pass and throttling

- One tick per side every 30 s; no per-unit or per-player timer is created by the Director (`95925-95927`).
- A Red tick always runs the defensive plan, intelligence decay, CAP reconciliation, region observation and strategic shadow update; only the operation build is conditional (`95842-95895`).
- Throttles and caches seen in the read code:
  - player-activity scores cached 15 s per variant (`75703`);
  - defensive-plan proposal reused up to 60 s while eight input signatures/generations are unchanged (`76862-76876`, `71063`);
  - strategic shadow recomputed only when `strategicShadowNextAt` passes or the planning inventory is rebuilt (`95771-95775`);
  - planning group inventory snapshot rebuilt every 300 s on the Blue/PvP path, and on demand for a Red plan, re-built during a plan only if `_reindexCombatFilterGeneration` changed (`95770-95773`, `94578-94621`);
  - strategic budget every 60–180 s, with log output only when the decision signature changes (`84325`, `84379-84388`);
  - ground release every 90 s, real eligibility tested for at most 12 candidates, shortlist of 6, route facts and blocked-pair results memoised per source/target pair within the pass (`85423`, `85432-85447`, `85266-85297`);
  - operation reassessment every 90 s (`70999`);
  - SEAD threat lookups go through a catalogue (`GetSeadThreatCatalog`) and zone-to-zone distances through the precomputed `ZONE_DISTANCES` table rather than live geometry (`79321-79322`, `79324`);
  - "generation" counters (`_capTargetStateGeneration`, cohort `generation`, `campaignActionGeneration`, `_runwayPlaneSpawnBlockGeneration`) are compared instead of re-deriving state (`95747`, `76859-76860`);
  - battlefield route memory is bounded to 128 rows (`71039`).
- The unconditional per-tick work that scans all zones is `_collectTargetCandidates` (every zone × its neighbours, with `_targetScore` including a SAM-exposure scan of the threat catalogue) when a plan or a ground release runs (`84776-84802`, `85259`).
- The engine changelog is not part of the extract (only `tools/FootholdConfigManager/CHANGELOG.md` exists), so the 6.4.6 note on reduced repeated processing could not be matched to code.

## Reproduction notes (whole theme)

- The Director needs no Moose: timers are `timer.scheduleFunction`, time is `timer.getAbsTime()`/`timer.getTime()`, randomness is `math.random`; the only Moose calls in the read parts are `UTILS.VecDist2D` and, in `BudgetCommander`, `SCHEDULER` (`75749`, `96283`).
- The hard part is not any single formula but the amount of shared state it reads from the rest of the engine: zone graph and precomputed distances, zone combat-strength snapshots, SEAD threat catalogue, CAP target ranking, player lists, the reactive pressure map, the shop, the mass-attack and bomber modules, and the `GroupCommander` FSM hooks (`allowsGroupSpawn`, `onGroupStateChanged`, `onManagedSpawnDenied`).
- Decisions are layered so that each layer can veto the next: campaign-action admission → posture → package build → per-assignment gates → `GroupCommander` spawn eligibility; a failure at any layer leaves the assignment unauthorised and it is retried on the next tick.
- Almost every choice is a weighted random among the top few candidates with hysteresis (hold times, confirmations, leases); reproducing only the scores without the hysteresis gives a jittery planner.
- Every piece of memory has a decay or an expiry and is saved as remaining time, which is what makes it survive a server restart without "waking up" stale.
