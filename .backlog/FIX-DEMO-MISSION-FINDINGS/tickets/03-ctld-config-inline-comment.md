# 03 — `ctld-config.yaml`: an end-of-line comment becomes part of the value

Status: ✅ done
Type: fix + validate
Files: build step that embeds `ctld-config.yaml` into `CTLD_userConfig.lua`, `validate`, `mission_builder/mission_builder_worker.py` (order of the embed), tests

## What happens

The build embeds `ctld-config.yaml` as text and CTLD parses it with its own YAML reader, which keeps an end-of-line comment as part of the value: `jtacLaserCodeMax: 1686   # …` becomes the string `"1686   # …"`, and CTLD's JTAC init fails on `CTLD.lua:22287: 'for' limit must be a number` (then ticket 02 takes the whole config down).
Standard YAML, `validate` and the build all read it as `1686`.

Second observation, **to confirm**: after editing `ctld-config.yaml`, the first build embedded the *old* value in the `.miz` while `src/scripts/CTLD_userConfig.lua` already held the new one; the next build was right. Hypothesis: the file is embedded before it is regenerated.

## Measured

Demo mission, 2026-10-05, `dcs.log` of the first in-game run; the lag seen once, on two consecutive builds.

## Fix

- Normalise what is embedded: re-serialise the parsed YAML (or strip end-of-line comments) so CTLD never sees one; or, at minimum, `validate` rejects an end-of-line comment in `ctld-config.yaml`, naming the line.
- Check the embed order and make the `.miz` carry the config generated by the same build.

## Demo workaround to remove

Comment moved to its own line; `tools/verify.py` rejects end-of-line comments in `ctld-config.yaml`.
